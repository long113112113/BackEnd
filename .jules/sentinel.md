## 2024-05-18 - [Fix CWE-208 Timing Leak in MQTT Auth]
**Vulnerability:** A classic timing leak was present in the `timingSafeEqual` utility within `src/config/aedes.js` because the code initially checked if the string lengths match, returning `false` early if they don't, before comparing with `crypto.timingSafeEqual`. This allows an attacker to deduce the lengths of valid usernames/passwords via a timing attack. Additionally, Node.js `crypto.timingSafeEqual` will throw an error and crash the application (DoS) if inputs have different lengths without this prior check, so it's a tricky balance without hashing.
**Learning:** Checking string lengths before doing a secure comparison bypasses the timing security and is a common pitfall. The correct way to compare two potentially different-length strings securely in Node.js without timing leaks and without risking unhandled length-mismatch exceptions is to hash both strings first using SHA-256 before comparing the hashes.
**Prevention:** Whenever `crypto.timingSafeEqual` is used, always ensure both inputs are hashed first (e.g., `crypto.createHash('sha256').update(buf).digest()`) to guarantee equal lengths, avoiding both timing leaks and application crashes.
